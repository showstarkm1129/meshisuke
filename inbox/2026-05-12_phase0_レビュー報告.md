#### W-1: `.gitignore` に `.claude/` の除外エントリがない

| 項目 | 内容 |
|---|---|
| **該当ファイル** | `app/.gitignore` |
| **該当箇所** | ファイル全体 |
| **現状** | `.claude/` ディレクトリ（`app/.claude/agent-memory/`）が `.gitignore` に記載されていない。`app/.claude/` ディレクトリは実際に存在する（`agent-memory/code-review-agent/`、`agent-memory/coding-agent/` を内包）。 |
| **問題** | エージェントが生成・更新するメモリファイル群が次回コミットの対象に混入する。意図しないエージェント内部状態のコミットはリポジトリの汚染につながる。ただし、メモリをバージョン管理下に置いてチームで共有する方針であれば除外しなくてよいため、プロジェクトの方針確認が先決。 |
| **推奨対応** | エージェントメモリをバージョン管理対象**外**にする場合は、`app/.gitignore` に以下を追記する。<br><br>```<br># Agent memory (internal use)<br>.claude/<br>```<br><br>チームで共有する方針（バージョン管理対象**内**）の場合は、その旨を `app/README.md` または `構成.md` に明記して混乱を防ぐ。どちらにせよ現状は未決定の状態であり、意思決定と記録が必要。 |
| **根拠** | `app/.claude/` ディレクトリが `app/.gitignore` のどのパターンにもマッチしていないため、`git status` で追跡対象に含まれる。また `構成.md` の役割定義・`CLAUDE.md` にも `.claude/` の取り扱い方針の記載はない。 |

#### W-2: `tsconfig.app.json` の `lib` に `DOM.Iterable` が含まれていない

| 項目 | 内容 |
|---|---|
| **該当ファイル** | `app/tsconfig.app.json`、5行目 |
| **該当箇所** | `"lib": ["ES2023", "DOM"]` |
| **現状** | `lib` に `ES2023` と `DOM` のみが指定されている。`DOM.Iterable` が含まれていない。これは Vite テンプレートが生成した値をそのまま引き継いでいる（Phase 0 の指示書はこの項目への変更を求めていなかった）。 |
| **問題** | File System Access API では `FileSystemDirectoryHandle` を `for await...of` で反復するパターンが多用される（例: `for await (const entry of dirHandle.values())`）。`DOM.Iterable` が `lib` にないと、`FileSystemDirectoryHandle` の非同期イテレーター型定義が TypeScript に認識されず、Phase 1 で型エラーが発生する可能性がある。`strict: true` が有効化されているため、エラーは抑制されずビルド失敗につながる。 |
| **推奨対応** | `app/tsconfig.app.json` の `lib` を以下のように変更することを検討する。<br><br>```json<br>"lib": ["ES2023", "DOM", "DOM.Iterable"]<br>```<br><br>Phase 1 で `for await...of` による反復を使わない場合（`FileSystemDirectoryHandle.values()` を `Array.from()` で変換する等）は影響が出ない可能性もあるため、Phase 1 着手時に型エラーが実際に発生するかを確認してから対処してもよい。 |
| **根拠** | TypeScript の `DOM.Iterable` は `DOM` lib では定義されていない非同期・同期イテレーター拡張型を追加する。File System Access API の `FileSystemDirectoryHandle` は `AsyncIterable<FileSystemHandle>` を実装しており、これを直接 `for await...of` で使う場合は `DOM.Iterable` が必要になる。 |

## 4. 総括コメント

Phase 0 の主要な実装判断はすべて適切だった。特に以下の点を評価する。

- `eslint-config-prettier` を `defineConfig` 配列の**末尾**に独立したオブジェクトとして配置した点。flat config において `eslint-config-prettier` は `files` を持たないため、末尾に置くことで他のすべてのルールセット（`tseslint.configs.recommended`、`reactHooks.configs.flat.recommended` 等）が有効化した後にスタイル競合ルールを上書き無効化できる。順序は正しい。
- `tsconfig.app.json` への `strict: true` 追加が、`noUnusedLocals`、`noUnusedParameters` 等の Linting ブロックの**前**（Strict type checking ブロック内）に置かれており、設定の意図が読みやすい。
- 実際のバージョン（Vite 8 / TypeScript 6 / Node.js 22）と指示書記載バージョン（Vite 6 / TypeScript 5 / Node.js 20）の乖離を適切に検出し、実バージョンで README を記載した判断は正しい。
- `eslint-plugin-react-hooks` の `rules-of-hooks: error` / `exhaustive-deps: warn` および `react-refresh/only-export-components: warn` が `reactHooks.configs.flat.recommended` と `reactRefresh.configs.vite` によって既に適切に設定されており、重複追記を避けた判断も正確。

完了報告で「未確認」と記載されている完了条件 2〜4（`npm install` / `npm run dev` / `npm run lint` の実際の動作確認）については、マネージャー側で確認済みとのことであり、Phase 0 のスコープ上の問題ではない。
