# プロンプト動的合成（PromptComposer）実装計画

作成日: 2026-05-27
ステータス: ドラフト（A案 + セクションマーカー方式で合意済み、要レビュー）

---

## 1. 背景・目的

現状 [app/src/lib/systemPrompt.ts](../app/src/lib/systemPrompt.ts) は `システムプロンプト.md`（762行）を **毎ターン全文** LLM に渡している。
入力トークンが固定で大きく、OpenRouter 経由でも以下の問題がある:

- 入力課金が会話長に対して線形でなく、毎ターン底値が高い
- 必要のない局面でも「裏側モード」「初回フォーム」等の詳細仕様が常に文脈にあり、モデルが誤発火する余地が残る
- プロンプト規模が大きいほど、優先順位（命令 > キャラ > モード規律 > 構造 > 提案）の遵守確率は単調に上がるわけではない（中盤の冗長指示はノイズ）

**目的**: 会話状態に応じて必要なセクションのみを連結して送る `PromptComposer` を導入し、典型ケースで **30〜60% のトークン削減** を狙う。
LangChain / LangGraph は導入しない（ブラウザ完結アーキと不釣り合いなため）。

---

## 2. 設計判断（合意済み・固定）

| # | 項目 | 決定 |
|---|---|---|
| 1 | フレームワーク採用 | **採用しない**（自前 PromptComposer） |
| 2 | プロンプト分割形式 | **1ファイル + セクションマーカー**（`システムプロンプト.md` を維持） |
| 3 | マーカー記法 | HTMLコメント `<!-- @section:NAME -->` ... `<!-- @endsection:NAME -->` |
| 4 | 状態判定の主体 | `useChat` 側で会話状態を判定し `PromptComposer.build()` に渡す |
| 5 | フォールバック | マーカー解析失敗時は **現状通り全文返却**（安全側） |

## 3. セクション設計

ユーザー提示の分類をそのまま採用する。

| セクションID | 概算行数 | 含まれる現プロンプトの章 | 含める条件 |
|---|---|---|---|
| `core` | ~200 | 命令 / 応答する前にこれを通す / キャラクター設定 / セルフチェック / 違反指摘時 | **常時** |
| `initial` | ~80 | セッション開始時の動作 / 初回フォームモード | `turns.length === 0` または `profile.onboarding_completed === false` |
| `continuing` | ~280 | 継続モード詳細 / レシピ提案フロー / 調味料管理 / 数量・単位正規化 | `turns.length >= 1` かつ `onboarding_completed === true` |
| `backside` | ~100 | 裏側モード / 内部スキーマ全文 | 直近のユーザー発話が裏側トリガーにマッチ、または直近5ターン以内に裏側応答実績あり |
| `pitfalls` | ~100 | よくある失敗パターン集（現状 core に内包されているなら分離） | **常時**（core に含めても良いが分離してオン/オフ可能にしておく） |

※ 現プロンプトの章構成と上記の対応関係は実装着手時に [システムプロンプト.md](../システムプロンプト.md) を全文確認してから確定する。
本計画の数字はユーザー提示の概算であり、実測で ±20% の誤差が出ても設計は変えない。

## 4. ファイル変更

### 4.1 `システムプロンプト.md`（既存ファイルへマーカー挿入）

各セクションの直前直後に HTML コメントマーカーを挿入する。
**本文は1文字も書き換えない**（git diff がマーカー追加のみになるようにする）。

```markdown
<!-- @section:core -->
# 命令
あなたは一人暮らしの20代をサポートする...
...（セルフチェックまで）
<!-- @endsection:core -->

<!-- @section:initial -->
## セッション開始時の動作
...
<!-- @endsection:initial -->

<!-- @section:continuing -->
## 継続モード
...
<!-- @endsection:continuing -->

<!-- @section:backside -->
## 裏側モード
...
<!-- @endsection:backside -->

<!-- @section:pitfalls -->
## よくある失敗パターン
...
<!-- @endsection:pitfalls -->
```

- マーカーは LLM への出力時には除去する（後述のパーサで）
- セクション間の地の文（章タイトルだけの行など）はどのセクションにも属さない「常時部」として core に組み込むか、明示的に core 末尾に追加するか、実装時に判断
- ネスト・順序入れ替えは v1 では対応しない（フラットなセクション列のみ）

### 4.2 `app/src/lib/promptSections.ts`（新規）

責務: マーカー付き .md をパースしてセクション辞書に分解する。

```ts
export type SectionId = 'core' | 'initial' | 'continuing' | 'backside' | 'pitfalls';

export interface ParsedSections {
  sections: Record<SectionId, string>;
  unknownSections: string[];   // マーカーIDがSectionIdに無い場合
  warnings: string[];          // 閉じタグ抜け等
}

export function parseSections(raw: string): ParsedSections;
```

- 正規表現で `<!-- @section:(\w+) -->([\s\S]*?)<!-- @endsection:\1 -->` を抽出
- マーカー外の本文は破棄せず `core` に末尾結合（フォールバック）
- パース失敗（マーカー閉じ忘れ等）は `warnings` に積むだけで例外は投げない
- **ユニットテスト対象**

### 4.3 `app/src/lib/promptComposer.ts`（新規）

責務: 会話状態 → 含めるセクション一覧の決定 + 文字列連結。

```ts
export interface ConversationState {
  turnsCount: number;
  onboardingCompleted: boolean;
  lastUserText: string | null;
  recentBacksideActivity: boolean;  // 直近5ターンに裏側応答があったか
}

export interface ComposeResult {
  prompt: string;
  includedSections: SectionId[];
  estimatedTokenSavings: number;   // 全文比のおおよその削減率（行数ベース）
}

export function decideSections(state: ConversationState): SectionId[];
export function composePrompt(
  sections: ParsedSections,
  state: ConversationState,
  dataSection: string,
): ComposeResult;
```

#### decideSections のロジック（v1）

```
always: [core, pitfalls]

if turnsCount === 0 || !onboardingCompleted:
  add: initial

if turnsCount >= 1 && onboardingCompleted:
  add: continuing

if isBacksideTrigger(lastUserText) || recentBacksideActivity:
  add: backside
```

#### 裏側トリガーの判定

- `lastUserText` に `/裏側|うらがわ|裏モード|データ見せ|JSON|スキーマ|デバッグ/` がマッチ
- または既存の `/backside` 系コマンド（[BacksideView.tsx](../app/src/components/BacksideView.tsx) のトリガー条件と揃える）
- 正規表現は `promptComposer.ts` 内の定数として切り出し、テスト可能にする

### 4.4 `app/src/lib/systemPrompt.ts`（既存ファイル改修）

`buildSystemPrompt` を以下のシグネチャに拡張:

```ts
export function buildSystemPrompt(
  data: AppDataState,
  conversation?: ConversationState,    // 省略時は従来動作（全文）
): { prompt: string; debug: ComposeResult | null };
```

- `conversation` を渡さない場合は **現状通り全文連結を返す**（後方互換）
- 渡された場合は `parseSections` → `decideSections` → `composePrompt` を経由
- パーサが `warnings` を返した場合、console.warn のみ。LLM には全文フォールバックで送る（安全側）
- 戻り値を `{ prompt, debug }` のタプルに変えるのは、開発時に「今何が含まれているか」を確認できるようにするため

### 4.5 `app/src/hooks/useChat.ts`（既存ファイル改修）

[useChat.ts:101](../app/src/hooks/useChat.ts#L101) の `buildSystemPrompt(state.data)` を以下に置換:

```ts
const conversation: ConversationState = {
  turnsCount: turns.length,
  onboardingCompleted: state.data.profile?.onboarding_completed ?? false,
  lastUserText: text,                       // 今送ろうとしているユーザー発話
  recentBacksideActivity: detectRecentBackside(turns),
};
const { prompt: systemPrompt, debug } = buildSystemPrompt(state.data, conversation);

if (import.meta.env.DEV && debug) {
  console.debug('[PromptComposer]', debug.includedSections, `${debug.estimatedTokenSavings}% saved`);
}
```

- `detectRecentBackside(turns)` は同ファイル内のユーティリティとして実装（直近5ターンに `toolNotices` を含むアシスタント応答があるか等で判定）

## 5. テスト方針

### 5.1 ユニットテスト（vitest 想定。未導入なら導入要件として別立て）

- `parseSections`:
  - 全セクション正常検出
  - セクション抜け（initial が無いプロンプト）でも他セクションは無事に取れる
  - 閉じタグ抜けで warnings に記録され、当該セクションは空文字
  - マーカー外本文が core に結合される
- `decideSections`:
  - `turns=0, onboarding=false` → `[core, pitfalls, initial]`
  - `turns=5, onboarding=true, 通常文` → `[core, pitfalls, continuing]`
  - `lastUserText='裏側見せて'` → `[core, pitfalls, continuing, backside]`
  - `onboarding=true, turns=0`（履歴クリア直後）→ `[core, pitfalls, initial]` （要決定。§9-A 参照）

### 5.2 手動 QA

- [ ] 初回起動（profile 未作成）で `initial` が含まれ、`continuing` が含まれないこと
- [ ] オンボーディング完了後の通常会話で `initial` が外れ `continuing` に切り替わること
- [ ] 「裏側見せて」と言うと次ターンから `backside` が含まれること
- [ ] 履歴クリア後、`continuing` のままで `initial` に戻らないこと（§9-A の決定次第）
- [ ] ペルソナ・口調が破綻していないこと（A/B で 5 ターンずつ）
- [ ] アレルギー違反提案が出ていないこと

### 5.3 トークン削減の実測

- DevTools の `[PromptComposer]` debug ログで `includedSections` を確認
- 各 LLM プロバイダの応答に含まれる usage（OpenRouter は返してくる）を1ターン分ログ採取
- 削減前後で 3 シナリオ × 5 ターン分の入力トークンを比較し、計画書末尾に追記する

## 9. 未決事項（実装着手前に確認したい点）

### 9-A. 履歴クリア後の挙動

`clearHistory` で `turns.length === 0` に戻った時、`onboarding_completed === true` ならどう振る舞う？

- (a) `initial` を再注入する（毎回挨拶モード）
- (b) `continuing` のままにする（プロファイルが存在するなら継続扱い）
- 現状コードは "セッション開始時の動作" を初回フォームと結合しているので、(b) を取るには `initial` を「初回フォーム」と「セッション開始の挨拶」に細分する必要あり

**ドラフト案: (b)**。理由はオンボーディング済みユーザーに「初めまして」を出す方が不自然なため。
ただしこれを採るなら `システムプロンプト.md` 内の「セッション開始時」記述を `core` 側に移すリファクタが要る。

### 9-B. `pitfalls` を `core` から分離するか

「よくある失敗パターン集」は現プロンプトでは独立した節になっておらず、各所に散っている可能性が高い。
分離せず core に統合するのも合理的で、その場合セクションは 4 つ（core / initial / continuing / backside）になる。
**ドラフト案: 分離しない**（実装簡素化のため）。ユーザー提示の構造とは少しズレるが効果は同じ。

### 9-C. ユニットテスト基盤の有無

[app/package.json](../app/package.json) に vitest / jest が入っていない。新規導入の是非を確認したい。
**ドラフト案: vitest を devDependencies に追加**（Vite との親和性が高く設定ほぼ不要）。

## 11. 実装結果と実測値（2026-05-27 追記）

### 11.1 セクション境界（実装後）

[システムプロンプト.md](../システムプロンプト.md) のマーカー位置:

| マーカー | 行 |
|---|---|
| `<!-- @section:core -->` | 1 |
| `<!-- @endsection:core -->` | 197 |
| `<!-- @section:initial -->` | 201 |
| `<!-- @endsection:initial -->` | 248 |
| `<!-- @section:continuing -->` | 252 |
| `<!-- @endsection:continuing -->` | 533 |
| `<!-- @section:backside -->` | 537 |
| `<!-- @endsection:backside -->` | 612 |
| `<!-- @section:core -->` (2nd block) | 616 |
| `<!-- @endsection:core -->` | 772 |

core が 2 ブロックに分かれるため、パーサは同一IDの複数出現を連結する実装にした。

### 11.2 シナリオ別削減率

`promptComposer.bench.test.ts` による実測。baselineLines = 773（マーカー込み・データ部除く）。

| シナリオ | 含めたセクション | 行数 | 削減率 |
|---|---|---|---|
| 初回起動（オンボ未完了） | core, initial | 405 / 773 | **48%** |
| 通常会話（オンボ済み中盤） | core, continuing | 639 / 773 | **17%** |
| 履歴クリア直後（オンボ済み） | core, continuing | 639 / 773 | **17%**（§9-A 通り initial を出さない） |
| 裏側モード起動 | core, continuing, backside | 716 / 773 | **7%** |

### 11.3 事前予想とのズレ

§1 と §3 の事前予想:
- 開始時のみ: 約63% 削減 → 実測 **48%**
- 中盤会話: 約37% 削減 → 実測 **17%**

**ズレの原因**: §9-B の決定により「よくある失敗パターン集」(行 616-772 / 約155行) を `core` に統合したため、`core` 自体が約 350 行と当初想定（200行）より大きくなった。失敗パターン集は規律維持に必須なので分離しない判断は維持するが、削減率は計画より控えめになる。

### 11.4 トレードオフの所感

- 「裏側モード」起動時の削減率 7% は小さいが、そもそも裏側モードは滅多に呼ばないので影響軽微
- 普段使い（オンボ済み中盤）で 17% 削減 → 1ヶ月単位の OpenRouter 課金には十分効く範囲
- 初回起動時の 48% 削減はオンボーディング体験のレスポンス改善に直結
- 失敗パターン集を `pitfalls` として独立セクション化し「中盤では含める / 安定運用後は外す」運用にすれば、中盤の削減率を 35%+ まで持っていける余地はある（v2 検討）

### 11.5 リリース後の観察ポイント

- `console.debug('[PromptComposer]')` ログで `includedSections` を観察し、想定通り切り替わっているか確認
- ペルソナ・口調の破綻が起きていないか（特に `pitfalls` を含む `core` が常時入っているので破綻しないはず）
- 裏側トリガーの正規表現が false positive を起こしていないか（"JSON" など一般語も含むため）
