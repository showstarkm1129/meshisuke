# 棚卸し UX 改善 実装計画

作成日: 2026-05-25
ステータス: ドラフト（ユーザー壁打ち合意済み、要レビュー）

---

## 1. 背景・目的

現状の `/manage` は全食材を 1 品ずつ対話形式で確認するため、20 品超の現実的な在庫では負荷が高く運用が続かない。
能動操作（テーブルでまとめて編集）と受動提示（緊急品だけ拾い上げる）に役割を分離し、認知負荷を下げる。

棚卸しは「思いついた時にやる」想定。毎日全件確認の前提を捨てる。

---

## 2. 設計判断（合意済み・固定）

| # | 項目 | 決定 |
|---|---|---|
| 1 | 重要度ヒアリングのコマンド名 | `/check` |
| 2 | 編集の保存タイミング | autosave（編集即反映） |
| 3 | `/manage` のリソース選択 | **複数選択可**（チップトグル） |
| 4 | リソース選択チップの粒度 | **概念単位（細粒度）**。アレルギー / 嫌い物 / 好み物 等を独立チップ化 |

---

## 3. アーキテクチャ概要

```
┌─ 能動: ユーザー主導 ────────────────────────────┐
│ /pantry, /profile, /history → 各テーブルを直接編集  │  ← Phase A
│ /manage  → 上記テーブルの「フィルタビュー」を集約表示 │  ← Phase B
└──────────────────────────────────────────────┘

┌─ 受動: めし助主導 ──────────────────────────────┐
│ /check → 緊急品をまとめて提示し一括処理               │  ← Phase C
└──────────────────────────────────────────────┘
```

役割分担：
- **能動系**は「全件を整える」/ **受動系**は「危ない品だけ拾う」
- /manage は専用ロジックを持たず、Phase A のテーブルコンポーネントを再利用するだけ

---

## 4. Phase A: 既存ビューの編集対応

### 4.1 対象ビュー

| ビュー | データソース | 編集対象 |
|---|---|---|
| `PantryView` | `pantry.json` | `ingredients[]` `seasonings[]` |
| `ProfileView` | `profile.json` | `allergies` `dislikes` `favorites` `dietary_restrictions` `daily_targets` `notes` |
| `HistoryView` | `meal_history.jsonl` | 行削除 / メモ追記（修正可否は要決定、§9-A 参照） |

### 4.2 編集 UI 仕様

- **セル直接編集**: クリックで `<input>` に切替、Enter / blur で確定
- **行削除**: 行末のゴミ箱アイコン
- **行追加**: テーブル末尾の「+ 新規」行
- **autosave**: onChange → デバウンス（300ms 想定）→ ファイル書き戻し
- **保存中表示**: テーブル右上に小さな「保存中... / 保存しました ✓」インジケータ

### 4.3 三値セマンティクス対応（重要）

`allergies` `dislikes` `favorites` は CLAUDE.md / README.md で **null / [] / 値あり** の三値を厳密に区別すると規定。
編集 UI で必ずこの三状態を表現する：

- セクションヘッダに状態トグル: **`未確認` / `確認済み`**
- `未確認` → データは `null`、テーブル本体は灰色マスク
- `確認済み` → データは `[]` 以上、テーブル本体が編集可能（空のままでも「該当なし」を意味する）

### 4.4 保存フロー

```
編集 → useAppState のディスパッチ → state 更新（楽観的）
       ↓
       File System Access API でファイル書き戻し
       ↓
       成功: 「保存しました」フラッシュ
       失敗: 「保存失敗、再試行」トースト＋ state ロールバック
```

ファイル単位で書き戻し（pantry.json 全体、profile.json 全体）。jsonl は追記/削除ベース。

---

## 5. Phase B: /manage フィルタビュー

### 5.1 コマンド挙動

1. `/manage` 入力 → チャットに「何を管理する？」メッセージ＋チップ列
2. ユーザーが複数チップをトグル選択
3. 「決定」ボタン → 選択リソースのテーブルが縦に並んで表示
4. 編集機能は Phase A の各テーブルコンポーネントをそのまま再利用 → autosave

### 5.2 リソース選択チップ（概念単位）

| キー | 対応データ |
|---|---|
| 食材 | `pantry.ingredients` |
| 調味料 | `pantry.seasonings` |
| 食事履歴 | `meal_history.jsonl` |
| アレルギー | `profile.allergies` |
| 嫌い物 | `profile.dislikes` |
| 好み物 | `profile.favorites` |
| 食事制限 | `profile.dietary_restrictions` |
| 栄養目標 | `profile.daily_targets` |
| プロフィール基本情報 | `profile.notes` ほか上記以外 |

### 5.3 実装方針

- リソースキー → React コンポーネント のマッピングを 1 つ用意（`getResourceTableView(key)`）
- /manage は選択キー配列を受け取り、対応コンポーネントを順に並べてレンダリングするだけ
- Phase A のコンポーネントを「フルビュー / 抜粋ビュー」両対応にしておくと再利用が綺麗

### 5.4 既存の対話型 /manage の扱い

- Phase B 完成時に**置き換え**（旧ロジック削除）
- 「対話的に 1 品ずつ確認したい」ニーズは Phase C (/check) が部分的にカバー

## 6. Phase C: /check 重要度ヒアリング

### 6.1 判定ロジック

`today` を基準として：

**食材 (`ingredients`)**
| 条件 | 緊急度 |
|---|---|
| `expires_at - today ≤ 0 日` | 🔴 期限切れ |
| `0 < expires_at - today ≤ 3 日` | 🔴 高 |
| `3 < expires_at - today ≤ 7 日` | 🟡 中 |
| 上記以外 | 表示なし |
| `expires_at` 欠損 | 表示なし |

**調味料 (`seasonings`)**
| 条件 | 表示 |
|---|---|
| `amount_current / amount_full < 0.2` | 🟠 残量少 |
| 上記以外 / `amount_full` が 0 や欠損 | 表示なし |

### 6.2 UI

- チャット内に緊急品を**一覧で一括表示**（1 品ずつ対話ではない）
- 各品にアクションチップ:
  - 食材: `まだある` / `使い切った` / `期限切れた`
  - 調味料: `補充済み` / `まだ少ない` / `使い切った`
- チップタップで即更新（autosave 経由）
- 全件処理しなくて OK、ユーザーは途中で離脱可能

### 6.3 起動

- **手動のみ**: `/check` 入力時
- アプリ起動時の自動チェックは **やらない**（§9-B で将来検討）

---

## 7. データモデル変更

**変更なし**。既存スキーマで全機能成立する。

- `expires_at` が空の食材は緊急度判定から除外（バリデーション側で警告は出さない）
- `amount_full` が欠損 / 0 の調味料は残量判定から除外

---

## 8. セキュリティ・データ規約遵守チェック

CLAUDE.md の禁止事項に照らして：

| 規約 | 遵守方法 |
|---|---|
| profile / pantry / meal_history を明示エンドポイント以外に送信しない | 編集は全てローカル File System Access API 経由。LLM への文脈付与は既存仕様を踏襲 |
| API キー / 個人情報をログに出さない | autosave エラー時のログは「フィールド名 + 失敗種別」のみ。値は出さない |
| File System Access API 以外の保存先を v1 で導入しない | 全保存パスを useAppState の既存ハンドラに集約 |
| `data/*.json` と型定義の同期 | 既存スキーマ流用のため新規同期作業なし。三値セマンティクスの型表現を確認 |

## 9. 未決・将来の論点

### A. 食事履歴の編集粒度
- 削除のみ / メモ追加可 / 全フィールド修正可 のどれか
- 案: v1 は **削除 + メモ追記** のみ、内容修正は別途検討（履歴改ざんの懸念）

### B. /check 自動起動
- 「朝アプリ開いた時に自動で出す」「3 日に 1 回」など
- v1 は手動のみ。利用ログが溜まってから判断

### C. 重要度しきい値カスタマイズ
- 3 日/7 日/20% を設定画面で変更可にするか
- v1 は固定値。ユーザーから要望が来てから対応

### D. 「未確認」状態のリセット
- profile.allergies を一度 `[]` にしてから `null` に戻す UI 必要か
- v1 はトグルで切替可能とする

## 10. 実装順序

1. **A.1** `PantryView` の inline-edit 化（最小ユニット、価値が最も大きい）
2. **A.2** File System Access API 書き戻しハンドラ整備（useAppState 拡張）
3. **A.3** `ProfileView` 編集対応（三値セマンティクス UI）
4. **A.4** `HistoryView` 編集対応（削除 + メモ追記）
5. **B**   `/manage` のフィルタビュー（テーブルコンポーネント再利用）
6. **C**   `/check` ヒアリング（判定ロジック + 一覧 UI + アクションチップ）

各ステップ完了時に手動動作確認。Phase 完了ごとにコミット。

## 11. 受け入れ基準（ユーザー視点）

- [ ] `/pantry` で玉ねぎの数量を 2 → 1 に変更 → pantry.json に反映される
- [ ] `/profile` でアレルギー欄を「未確認」→「確認済み」に切替 → `null` → `[]` に変わる
- [ ] `/manage` で「食材」「調味料」「アレルギー」を複数選択 → 3 つのテーブルが縦に並ぶ
- [ ] `/check` で期限 3 日以内の食材と残量 20% 未満の調味料がまとめて表示される
- [ ] `/check` 結果の「使い切った」チップタップ → 当該食材が pantry.json から削除される
- [ ] 編集中にネットワーク無関係でファイル書き込みが行われる（オフライン動作）
