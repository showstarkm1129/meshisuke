# 実装計画: エラーメッセージのユーザー向け整備

**作成日**: 2026-05-27
**ステータス**: 着手中
**背景**: チャット周りのエラー表示が `OpenRouter API error: 400 - ...` のような
HTTP ステータス羅列で、ユーザーが「自分のミスなのか／サービスのレート制限なのか／
バグなのか」を判別できない。原因クラス別に文言を整える。

---

## 設計方針

1. **HTTP ステータス別に文言を分岐**し、各ケースで *次の行動* を必ず含める。
2. プロバイダー名は内部値 (`openrouter`/`gemini`) ではなく `PROVIDER_LABELS` の表示名を使う。
3. `Chat Error:` の冗長 prefix は廃止（既に ErrorBanner が「エラーが発生しました」を見出しに出している）。
4. 開発者向けの生のレスポンス body は `console.error` 側に残し、UI は要約のみ。
5. ネットワーク失敗（DNS / オフライン / CORS など `TypeError: Failed to fetch`）も拾って固有文言を出す。

## HTTP ステータス → 文言マッピング

| ステータス | ユーザー文言（共通形）|
|---|---|
| 400 | 「{provider} へのリクエストが拒否されました: {message}。設定画面のモデル ID や入力内容を確認してください。」 |
| 401 | 「{provider} の API キーが認証されませんでした。設定画面でキーを再登録してください。」 |
| 402 | 「{provider} のクレジット残高が不足しています。ダッシュボードで残高を確認してください。」 |
| 403 | 「{provider} の API キーにこのモデルへのアクセス権がありません。キーの権限設定やプランを確認してください。」 |
| 404 | 「{provider} に指定モデルが存在しません。モデル ID のタイポや `-it` / `:free` などの suffix を確認してください。」 |
| 408 / 504 | 「{provider} の応答がタイムアウトしました。少し時間を置いて再送してください。」 |
| 429 | 「{provider} がレート制限中です（アクセス集中の可能性）。30 秒ほど待つか、別モデル（例: `deepseek/deepseek-chat`）に切替えてください。」 |
| 500〜599 | 「{provider} 側で一時的なエラーが発生しています ({status})。少し待って再送してください。」 |
| その他 | 「{provider} がエラーを返しました ({status}): {message}」 |
| ネットワーク失敗 | 「{provider} に接続できませんでした。インターネット接続を確認してください。」 |

---

## 検証手順

1. `tsc --noEmit` / ESLint / `vite build` がすべて通る
2. 手動: 既知の OpenRouter モデル ID で 1往復成功
3. 手動: 意図的に間違ったモデル ID を入力 → 400 文言が「モデル ID を確認してください」を含むこと
4. 手動: 意図的に API キーを空 / でたらめに → 401 文言になること（キー空は既に useChat で先回り検知）
5. 手動: 一時的にネット切断 → ネットワーク文言が出ること
