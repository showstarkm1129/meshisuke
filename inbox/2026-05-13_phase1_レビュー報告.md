#### W-1: `useFolderPicker.ts` — `SET_DIR_HANDLE` の二重 dispatch によるデータ読み込みの二重起動リスク

- **場所**: `app/src/hooks/useFolderPicker.ts` 22行目・48行目
- **現状**:

```typescript
// 22行目（バリデーション前）
dispatch({ type: 'SET_DIR_HANDLE', payload: rootHandle });

// ...data/ 存在確認・必須ファイル確認...

// 48行目（バリデーション通過後）
dispatch({ type: 'SET_DIR_HANDLE', payload: rootHandle });
```

- **問題**: `FolderPicker.tsx` の `useEffect` は `state.dirHandle` の変化を監視して `loadData()` を呼ぶ。22行目の dispatch で `dirHandle` が最初にセットされると `loadData()` が即座に起動する。その時点では必須ファイル確認がまだ完了していないため、`data/` ディレクトリが存在しないフォルダを選んだ場合でも読み込み処理が走ってしまう。48行目は最終的に同じ値を dispatch するため State の変化がなく `useEffect` は再発火しないが、22行目の dispatch がある限り「バリデーション前に読み込みが始まる」流れは変わらない。実データがある場合は問題が表面化しにくいが、`data/` なしフォルダ選択時にエラーが重複する可能性がある。
- **根拠**: `FolderPicker.tsx` 12〜16行目 `useEffect`。`useFolderPicker.ts` の 22行目で `dirHandle` がセットされると、その時点で `loadData()` が呼ばれる。
- **推奨対応**: バリデーション前の 22行目の dispatch を削除し、48行目（バリデーション通過後）の dispatch のみ残す。これで「バリデーション済みのハンドルのみが State に入る」という設計に整合する。

```typescript
// 22行目の dispatch を削除
// const rootHandle = await window.showDirectoryPicker({ mode: 'readwrite' });
// dispatch({ type: 'SET_DIR_HANDLE', payload: rootHandle }); // ← 削除

const dataHandle = await findDataDirectory(rootHandle);
// ...バリデーション...

// バリデーション通過後のみ dispatch
dispatch({ type: 'SET_DIR_HANDLE', payload: rootHandle });
```

#### W-2: `AppStateContext.tsx` の `initialState` — `localStorage` の値が不正な場合にアプリ状態が壊れる

- **場所**: `app/src/providers/AppStateContext.tsx` 16行目
- **現状**:

```typescript
saveMode: (localStorage.getItem('meshisuke_save_mode') as SaveMode) ?? SaveModeConst.Auto,
```

- **問題**: `localStorage.getItem('meshisuke_save_mode')` が `null` 以外を返す場合、`as SaveMode` キャストのみで値を採用している。ブラウザのローカルストレージは外部から書き換え可能であり、`'auto'` / `'manual'` 以外の文字列（例: `'hacked'`）が入っていた場合、型キャストが無条件で通るため実行時は不正な `saveMode` が State に設定される。`?? SaveModeConst.Auto` は `null` / `undefined` にしか反応しないため、空文字列や不正値はフォールバックしない。
- **根拠**: `SaveMode` は `'auto' | 'manual'` のユニオン型（`data.types.ts` 128〜132行目）。TypeScript の `as` キャストは実行時には何もしない。
- **推奨対応**: `localStorage` からの取得値を検証してからキャストする。

```typescript
function parseSaveMode(raw: string | null): SaveMode {
  if (raw === SaveModeConst.Auto || raw === SaveModeConst.Manual) return raw;
  return SaveModeConst.Auto;
}

const initialState: AppState = {
  // ...
  saveMode: parseSaveMode(localStorage.getItem('meshisuke_save_mode')),
  // ...
};
```

#### W-3: `file-system-access.d.ts` — DOM lib に既存の型を宣言しているため TypeScript バージョンアップ時に衝突する可能性

- **場所**: `app/src/types/file-system-access.d.ts` 全体
- **現状**: `Window.showDirectoryPicker` / `showOpenFilePicker` / `showSaveFilePicker` の 3 メソッドを `declare global` で宣言している。完了報告によると、`tsconfig.app.json` の `lib: ["ES2023", "DOM", "DOM.Iterable"]` で DOM 型が取り込まれているにもかかわらず、TypeScript のバージョンによっては `FileSystemDirectoryHandle` は認識されるが `Window.showDirectoryPicker` の型が欠落しているため追加したとのこと。
- **問題**: TypeScript 6.x は比較的新しく、将来のバージョンで DOM lib が `showDirectoryPicker` の型を正式収録した場合、このファイルの宣言と衝突する。現時点では動作しているが、`tsconfig.app.json` の `"types": ["vite/client"]` により DOM 型のサブセットしか取り込まれていない可能性があり、実際に `showDirectoryPicker` が欠落している原因が `types` 指定にある疑いがある（`types` を指定すると `@types/*` の自動インクルードが抑制されるが、`vite/client` は `Window.showDirectoryPicker` を含まない）。
- **根拠**: `tsconfig.app.json` 7行目 `"types": ["vite/client"]`。TypeScript の `lib` オプションと `types` オプションは別の機構（`lib` は組み込みライブラリ型、`types` は `@types` パッケージの自動インクルード制御）。
- **推奨対応（要確認）**: `tsconfig.app.json` の `"types": ["vite/client"]` に `vite/client` のみが指定されていることが原因かどうかを `npm run typecheck` の実際のエラーメッセージで確認してから、`file-system-access.d.ts` を維持すべきか削除すべきかを判断すること。短期的には現状の `.d.ts` ファイルで問題ないが、将来の衝突リスクとして認識しておくこと。なお、現状の宣言内容自体（オプション型・引数名など）は WHATWG 仕様と概ね整合しており品質は高い。

#### S-1: `fileio.ts` — 型ガード関数の戻り値型が `boolean` であり TypeScript の型絞り込みに連動しない

- **場所**: `app/src/lib/fileio.ts` 181行目 / 194行目 / 208行目
- **現状**:

```typescript
export function isValidProfile(value: unknown): boolean { ... }
```

- **問題**: 戻り値型が `boolean` のため、TypeScript は `if (isValidProfile(raw))` のブロック内で `raw` を `Profile` 型に絞り込めない。このため呼び出し側（`useDataLoader.ts` 39行目）では `raw as Profile` キャストが必要になっている。型ガードの慣用的な書き方 `value is Profile` を使えば `as Profile` キャストが不要になり、型の流れがより安全になる。
- **根拠**: TypeScript の型述語 (type predicate) の用途がまさにこのケース。
- **推奨対応**: Phase 2 以降で対応してよい。戻り値型を `value is Profile` 形式に変更することを推奨。

```typescript
export function isValidProfile(value: unknown): value is Profile {
  if (typeof value !== 'object' || value === null) return false;
  const obj = value as Record<string, unknown>;
  return (
    typeof obj['onboarding_completed'] === 'boolean' &&
    typeof obj['created_at'] === 'string' &&
    typeof obj['updated_at'] === 'string'
  );
}
```

これにより `useDataLoader.ts` 側の `raw as Profile` キャストを削除できる。

#### S-2: `ErrorBanner.tsx` — `key={i}` に配列インデックスを使用しているためエラー順序変化時に React の差分計算が不正確になる

- **場所**: `app/src/components/ErrorBanner.tsx` 13行目
- **現状**:

```tsx
{state.errors.map((msg, i) => (
  <li key={i}>{msg}</li>
))}
```

- **問題**: `key` に配列インデックスを使うと、エラーリストの先頭に新しいエラーが挿入された場合など順序が変化したときに React の reconciliation が誤った DOM 再利用を行う可能性がある。Phase 1 の `ADD_ERROR` は末尾追加のみなので現状では実害は小さいが、将来 `errors` の管理方法が変わると問題になりうる。
- **推奨対応**: Phase 2 以降で対応してよい。エラーに一意な ID を付与する（例: `crypto.randomUUID()` や連番カウンタ）か、メッセージ文字列自体を key にする（重複メッセージがないことを前提とする場合）。

```typescript
// Action の payload にエラー ID を付与する例（Phase 2 以降での検討）
type ErrorEntry = { id: string; message: string };
```

#### S-3: `useDataLoader.ts` / `useFileSaver.ts` — コンポーネントアンマウント後の `dispatch` 呼び出しに対するガードがない

- **場所**: `app/src/hooks/useDataLoader.ts` 全体、`app/src/hooks/useFileSaver.ts` 全体
- **問題**: `loadData()` や `saveProfile()` 等は `async` 関数であり、非同期処理中にコンポーネントがアンマウントされた場合、`finally` 等で `dispatch({ type: 'SET_LOADING', payload: false })` が呼ばれる。React 19 ではアンマウント後の State 更新に対する警告が緩和されているが、アプリが複雑になった場合に問題が顕在化する可能性がある。
- **推奨対応**: Phase 1 スコープでは許容範囲。Phase 2 以降でチャットストリーミング等の長時間非同期処理が加わるタイミングで `AbortController` または `useRef` によるマウント状態追跡の導入を検討すること。

---

#### S-4: `useFileSaver.ts` — `flushAll` が `saveMode` に関係なく実行できる

- **場所**: `app/src/hooks/useFileSaver.ts` 121行目 `flushAll` 関数
- **現状**: `flushAll` は手動保存モード専用という設計意図がコメントで説明されているが、`saveMode` チェックが関数内に存在しない。自動保存モード中に `flushAll` を誤って呼ぶと、自動保存で既に書き込まれたデータに対して再度書き込みが発生する（結果は同じでも意図しない処理）。
- **推奨対応**: Phase 2 以降での UI 実装時に対応でよい。`flushAll` の冒頭に `if (state.saveMode !== SaveMode.Manual) return;` を追加することを推奨。

## 5. 総括コメント

### 良好な点

- **`const enum` 禁止・`verbatimModuleSyntax` 対応**: 申し送り事項をすべて遵守している。`SaveMode` の `as const` オブジェクトパターンは適切。
- **`writeJsonFile` / `appendJsonlRecord` のエラー処理**: `createWritable` 後に `try/catch/abort` の構造で writable を確実に閉じており、ファイルの中途半端な書き込み状態を防いでいる。
- **Lint エラーへの対応（`react-refresh/only-export-components`）**: `AppStateContext` インスタンスを `useAppState.ts` に分離する対応は設計上も正しく、コンポーネントファイルを純粋なコンポーネント export に保つ良い判断。
- **型定義と実データの整合性**: `data.types.ts` の型は `data/*.json` の実構造と正確に一致している。`allergies` / `dislikes` / `favorites` が `WeightedItem[] | null`（未確認を null で表現）という設計もシステムプロンプトの意図と整合する。
- **JSONL 追記の実装コメント**: File System Access API に append mode がないことを明記し、全件読み込み→追記→上書きの理由をコメントで説明している。設計意図が明確。
- **`AbortError` のキャンセル処理**: ユーザーキャンセルをエラーとして表示しない処理が正しく実装されている。

### アーキテクチャ上の注意事項（情報共有）

`useAppState.ts` が `hooks/` ディレクトリに置かれているが、実質的には Context インスタンスの定義と Action 型の定義を担っており、通常の「カスタムフック」の責務を超えている。Lint エラー回避のための分離として合理的な判断だが、Phase 2 以降で `AppStateContext` の役割が拡大する際にはディレクトリ配置を再評価してよい（例: `hooks/useAppState.ts` のままで問題ないが、`types/actions.ts` に Action 型を分離する選択肢もある）。
