# pantry 差分ツール導入（在庫消滅バグ対策）実装計画

作成日: 2026-05-29
ステータス: ドラフト（差分ツール方式・要決定事項すべて合意済み、実装着手可）
対象モデル: `gpt-oss-20b:free`（非力なモデルでも壊れないことを最優先）

---

## 1. 背景・問題

チャット終了後の裏側データ連携に2つの不具合がある。

### 問題1: 少し使っただけの食材が完全消滅する（構造的バグ・本計画の主目標）

`update_pantry` は **pantry オブジェクト全体を丸ごと差し替える** 設計になっている。

- [tools.ts:5](../app/src/lib/tools.ts) — `update_pantry` は `pantry` 全体を required で受け取る
- [useChat.ts:172](../app/src/hooks/useChat.ts) — `savePantry(tc.arguments.pantry)` をそのまま渡す
- [useFileSaver.ts:48](../app/src/hooks/useFileSaver.ts) — `writeJsonFile(fh, pantry)` で**全置換**

このため、1品の数量を減らすだけでもモデルは全品目を再構築して返す必要があり、2つの破壊が起きる:

1. **省略＝削除**になる。弱いモデルは配列再構築時に一部品目を落とし、落とした品目は丸ごと消える。
   プロンプトに「`quantity=0` でもすぐ削除するな」と書いても、*メカニズムが全置換なので省略した瞬間に消える* ため無力。
2. **忠実に再現できない**。ツールは `purchased_at` を required にしている（[tools.ts:27](../app/src/lib/tools.ts)）が、
   システムプロンプトの在庫要約（[systemPrompt.ts:55-58](../app/src/lib/systemPrompt.ts)）には `purchased_at` が**含まれていない**。
   seasonings も実数ではなく `%` しか渡していない（[systemPrompt.ts:65](../app/src/lib/systemPrompt.ts)）。
   完璧なモデルでも欠損フィールドを捏造するしかなく、データが壊れる。

### 問題2: 「統合した」と言うのに何も変わらない

`gpt-oss-20b:free` は function calling 信頼性が低く、本文で「更新したよ」と言いながら
ツール呼び出しを発行しない、または `typeof === 'object'` ガードで弾かれるケースが多い。
[useChat.ts:168](../app/src/hooks/useChat.ts) はツール呼び出しが無ければ黙ってスルーするため、ユーザーには「言っただけ」に見える。

## 2. 設計方針（合意済み）

| # | 項目 | 決定 |
|---|---|---|
| 1 | pantry 更新の粒度 | **全置換をやめ、差分（delta）マージ方式に変更** |
| 2 | 弱いモデル前提 | モデルが出すべき情報を「変更する品目だけ」に最小化する |
| 3 | 削除の扱い | 削除は **明示フラグ必須**。省略では絶対に消えないようにする |
| 4 | 既存 `update_pantry` | 当面残すか撤去するかは §6 で判断（裏側モードの一括編集用途を考慮） |
| 5 | プロンプト | 差分ツール前提の呼び出しルールに刷新（§5） |

**核心**: 弱いモデルは「玉ねぎ -1」だけ出せばよい状態にする。全配列を触らせない＝省略事故が原理的に起きない。

## 3. 新ツール設計

### 3.1 `adjust_pantry_items`（食材の差分更新）

既存 `pantry.ingredients` に対し、**指定された品目だけ**をマージする。未指定の品目はそのまま保持する。

```jsonc
{
  "name": "adjust_pantry_items",
  "description": "食事確定や買い足しで、指定した食材の在庫だけを増減・追加・削除する。指定しなかった食材は一切変更されない。",
  "parameters": {
    "items": [
      {
        "name": "string",          // 必須。既存品目とのマッチキー
        "delta": "number",         // 任意。現在数量への増減（-1 で1減らす）。set と排他
        "set": "number",           // 任意。数量を絶対値で上書き（買い足し等）。delta と排他
        "remove": "boolean",       // 任意。true のときだけ削除。省略では絶対に消えない
        "unit": "string",          // 新規追加時のみ必須
        "purchased_at": "string",  // 新規追加時のみ。省略時は当日
        "expires_at": "string",    // 新規追加時の任意
        "storage": "冷蔵|冷凍|常温|野菜室", // 新規追加時の任意
        "note": "string"           // 任意
      }
    ]
  }
}
```

### 3.2 マージ規則（コード側で実装。モデルには委ねない）

`mergePantryItems(current: Ingredient[], items): Ingredient[]` を新規実装する:

1. `name` で既存品目を検索（正規化マッチ。大文字小文字・全半角の揺れは最低限吸収）
2. 既存あり:
   - `remove === true` → 配列から除外
   - `set` あり → `quantity = set`
   - `delta` あり → `quantity = max(0, quantity + delta)`（**負はクランプ**）
   - その他フィールド（note 等）は渡された分だけ上書き、渡されないフィールドは**保持**
3. 既存なし:
   - `remove === true` → 何もしない（no-op）
   - それ以外 → 新規追加。`unit` 欠落なら追加失敗としてスキップ＋警告ログ。
     `purchased_at` 省略時は当日、`expires_at`/`storage`/`note` は妥当なデフォルト
4. **`quantity=0` でも自動削除しない**（履歴・期限が次回判断に有用。システムプロンプト§数量正規化と整合）
5. 完了後 `pantry.updated_at` を当日に更新

### 3.3 調味料の差分（`adjust_seasonings`）

seasonings も同型の問題を抱える（要約が `%` のみ）。同方針で差分ツールを用意する:

```jsonc
{
  "name": "adjust_seasonings",
  "parameters": {
    "items": [
      { "name": "string", "delta_ml_or_g": "number", "refill_full": "boolean" }
    ]
  }
}
```

- `delta_ml_or_g` → `amount_current = clamp(0, amount_current + delta, amount_full)`
- `refill_full: true` → `amount_current = amount_full`（「醤油買ってきた」）
- 未指定の調味料は保持

> 補足: 調味料の自動減算はシステムプロンプト「調味料の裏側管理」で推定ベースと規定済み。
> ツールはその推定値（`delta_ml_or_g`）を受け取るだけにし、換算はモデル側に任せる。

## 6. 決定事項（合意済み）

1. **`update_pantry` は対話モードから撤去**
   - 裏側モードでのみツール一覧に含める（バックアップ復元・一括上書き用途）
   - [useChat.ts:163](../app/src/hooks/useChat.ts) で `tools: TOOLS` を渡している箇所を、`conversation.recentBacksideActivity || isBacksideTrigger(...)` で出し分け
   - description にも「裏側モード専用」と明記し、誤発火を二重に防ぐ

2. **name マッチの正規化はコード側では最小限。意味的な表記揺れは LLM に委ねる**
   - コード側の正規化: **前後空白・全半角・大文字小文字の吸収のみ**（trim 相当）
   - 「鶏もも ≒ 鶏もも肉」「玉ねぎ ≒ タマネギ」のような意味マッチは LLM 判断に任せる
   - プロンプトに「`name` は在庫要約に出ている正式名と完全一致させる。在庫に無いものを追加するときだけ新規名を使ってよい」を追記（追加 30〜50トークン）
   - **二重登録防止の保険**: 完全一致しなかった `delta` 指定は新規追加せず、開発時 `console.warn` で可視化。
     ユーザーが裏側モードで統合できるようにする
   - （`set` / `remove` の場合も同様。完全一致しない既存項目への操作は no-op + warn）

3. **実機検証はユーザーが実施**
   - コード側の単体テスト（`pantryMerge.test.ts`）は実装に含める
   - 実機での消滅再現→修正後検証はユーザーが対応するため、本計画からは外す
