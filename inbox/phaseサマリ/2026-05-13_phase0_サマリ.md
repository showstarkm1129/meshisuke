## 3. アーキテクチャ判断のハイライト

### なぜ Vite + React + TypeScript なのか

実装計画（`2026-05-12_実装計画_MVP.md`）に「フロントエンド: React + Vite + TypeScript / `npm create vite@latest` テンプレートから開始」と確定事項として明記されている。

この組み合わせの採用理由は「ブラウザだけで完結するローカル Web アプリ」という設計方針と整合している。Vite はバンドラと開発サーバーを兼ねるため、バックエンドサーバー不要の構成でも開発体験を損なわない。React はコンポーネント単位のUI設計を可能にし、Phase 3 以降で実装するチャット画面・裏側モードのような複数の異なる画面モードを管理するのに適している。TypeScript は型安全性を担保し、Phase 1 以降で扱うファイルI/Oや LLM APIのレスポンス（形状が不定になりがちなデータ）を扱う際の誤りを早期に検知する。

なお、実際に初期化されたテンプレートは Vite 8 / React 19 / TypeScript 6 と、指示書が想定していた Vite 6 / TypeScript 5 よりも新しかった。coding-agent はこの差分を適切に検出し、README のバージョン表記も実バージョンで記述している。

### なぜ File System Access API なのか（バックエンドレスとの関係）

実装計画の「確定事項」に「ローカルファイル: File System Access API / Chrome / Edge 限定で割り切る」と明記されている。

この選択の本質は「食生活データを第三者サーバーに送らない」という設計原則にある。プロジェクト全体の README にも「食生活データが第三者サーバーに送信されない設計」と明記されており、バックエンドを持たない構成が前提だ。File System Access API はブラウザから直接ユーザーのローカルファイルを読み書きできる標準 API であり、サーバーを介さずに `data/*.json` や `meal_history.jsonl` を永続化する唯一の現実的な選択肢となる。

非対応ブラウザ（Firefox / Safari）への対応は MVP スコープ外とし、「Chrome / Edge 限定で割り切る」という意思決定がなされている。これはエンジニアリングの割り切りではなく、「個人データをサーバーに送らない」というプロダクトの価値観を守るための選択である。

### なぜ ESLint flat config の末尾に prettier を置いたのか

`eslint.config.js` では `defineConfig` 配列の末尾に `prettier`（`eslint-config-prettier`）を独立したオブジェクトとして配置している。

```js
export default defineConfig([
  globalIgnores(['dist']),
  {
    files: ['**/*.{ts,tsx}'],
    extends: [
      js.configs.recommended,
      tseslint.configs.recommended,
      reactHooks.configs.flat.recommended,
      reactRefresh.configs.vite,
    ],
    // ...
  },
  prettier,  // <-- 末尾に配置
])
```

ESLint のルールは配列の後ろにあるものが前のものを上書きする。`eslint-config-prettier` はインデントや引用符などスタイル系ルールを「オフ」にするルールセットであり、末尾に置くことで先行するすべてのルール（TypeScript-ESLint・React Hooks・React Refresh）が有効化された後にスタイル競合ルールだけを上書き無効化できる。また、`eslint-config-prettier` は `files` を持たないオブジェクトのため、すべてのファイルに対してスタイルルールの競合を解消する。この配置はレビュー報告書（code-review-agent の総括コメント）でも「正しい」と評価されている。

### なぜ strict + DOM.Iterable なのか

`tsconfig.app.json` の `strict: true` は、型チェックを最大限に厳密にするフラグだ。Phase 1 以降で扱う File System Access API のレスポンスや LLM API のレスポンスは外部データであり、型推論が甘いと実行時エラーが検知できない。`strict: true` を Phase 0 の段階で有効にしておくことで、後のフェーズで書かれるコードが最初から厳密な型チェックを受ける環境を整えた。

`DOM.Iterable` の追加は code-review-agent（W-2 指摘）により Phase 0 完了後に対処された。File System Access API では `FileSystemDirectoryHandle` を `for await...of` で反復するパターンが多用される（例: `for await (const entry of dirHandle.values())`）。`DOM.Iterable` が `lib` になければ TypeScript は `FileSystemDirectoryHandle` の非同期イテレーター型定義を認識できず、`strict: true` が有効な状態ではビルドエラーになる。Phase 1 で実際に型エラーが発生する前に、この追加が完了している。

## 4. ディレクトリ構成の意図

`app/src/` 配下に以下の 6 ディレクトリを定義した。現時点では各ディレクトリに `.gitkeep` のみが存在し、実装コードはない。

```
app/src/
├── components/     # UI コンポーネント（再利用可能なもの）
├── hooks/          # カスタム React フック
├── lib/            # ユーティリティ・ビジネスロジック（フレームワーク非依存）
├── providers/      # LLM プロバイダー実装・コンテキストプロバイダー
├── types/          # TypeScript 型定義（*.types.ts / *.d.ts）
└── pages/          # ページ単位のトップレベルコンポーネント
```

各ディレクトリの受け持ちと、後のフェーズとの対応を以下に示す。

| ディレクトリ | 受け持ち | 主に使われるフェーズ |
|---|---|---|
| `components/` | ボタン・入力フォーム・メッセージバブルなど、複数のページで再利用される UI パーツを置く。ページ固有のロジックは持たない | Phase 3（チャット UI） |
| `hooks/` | ファイルI/Oの状態管理・LLM接続状態など、React コンポーネントからロジックを切り出したカスタムフックを置く。コンポーネントを薄く保つための分離層 | Phase 1（ファイルI/O）〜 Phase 3 |
| `lib/` | React に依存しない純粋なユーティリティ関数・ビジネスロジックを置く。JSON パース・JSONL の読み書き・スキーマ検証など。フレームワーク非依存であるため、テストが書きやすい | Phase 1（ファイルI/O）〜 Phase 2 |
| `providers/` | LLM プロバイダー（Claude・Gemini）の実装と、React Context を通じてアプリ全体に状態を提供するコンテキストプロバイダーを置く。実装計画では「`LLMProvider` インターフェース定義 → Claude 実装 → Gemini 実装」の順序が決まっている | Phase 2（LLMプロバイダー抽象化） |
| `types/` | TypeScript の型定義ファイルを置く。`profile.json` や `pantry.json` のスキーマを TypeScript 型として定義することで、アプリ全体で型安全なデータ操作ができる | Phase 1〜 全体 |
| `pages/` | チャット画面・裏側モードなど、ルーティングの単位になるページコンポーネントを置く。将来のルーティング拡張（React Router等の導入）を見越した配置 | Phase 3〜 Phase 4 |

補足: `providers/` ディレクトリは Phase 1 ではまだ使われないが、Phase 2 で LLM プロバイダー抽象化レイヤーを実装する際の受け皿として Phase 0 の段階で作成されている。これは「先にディレクトリ規約を決めておくことで、後のフェーズで場当たり的なディレクトリ追加を防ぐ」という判断である。

## 5. エージェント協働プロセスの所見

Phase 0 では以下の 3 段サイクルを実施した。

```
[1] Manager-agent  → 指示書作成（2026-05-12_phase0_指示書.md）
[2] Coding-agent   → 実装（設定ファイル・ディレクトリ骨格の作成・編集）
[3] Code-Review-agent → レビュー（2026-05-12_phase0_レビュー報告.md）
     ↓ main Claude が W-1・W-2 を評価・対処
[4] Content-agent  → 本サマリ作成
```

### 機能した点

- **役割の明確な分離が機能した**: coding-agent は「指示書通りの実装のみ」を担い、レビューと意思決定は別エージェントが担当した。このおかげで coding-agent の完了報告は実装の事実（何を変えたか）のみを記述しており、判断の混入がなかった。

- **code-review-agent が実害のある問題を事前に検出した**: W-2（`DOM.Iterable` 欠落）は、Phase 1 で File System Access API を使い始めるまで顕在化しない問題だった。コードを書く側ではなく、独立したレビュアーが「次のフェーズで何を使うか」を踏まえてレビューしたことで、Phase 1 着手前に対処できた。

- **W-1（.gitignore の二重記載）については main Claude が上位ファイルを確認して正しく棄却した**: code-review-agent がルートの `.gitignore` を参照していなかったため W-1 を指摘したが、main Claude がルートの `.gitignore` に `.claude/` が既に含まれていることを確認し、対処不要と正しく判定した。この「レビュー結果を鵜呑みにせず、上位ファイルとの整合性を確認してから意思決定する」フローが重要だった。

### 改善・学習された点

- **バージョン乖離への対応**: 指示書は Vite 6 / TypeScript 5 を前提に書かれていたが、実際のテンプレートは Vite 8 / TypeScript 6 だった。coding-agent はこの乖離を検出し、実バージョンで README を記載する判断を行った。指示書作成時点でのバージョン固定（`npm create vite@latest` のバージョン指定）は今後の指示書で検討すべき改善点である。

- **「未確認」として残った完了条件**: coding-agent は `npm run lint` の実際の動作確認ができず「未確認」として報告した。bash を持たない coding-agent の制約から来る分担上の問題であり、レビュー報告でも問題なしと評価されている。Phase 1 以降でも同様の分担（実行は main Claude、ファイル編集は coding-agent）が続く。

## 6. Phase 1 へのバトン

### Phase 1 のスコープ（実装計画より）

- File System Access API でルートフォルダ選択 → `data/` 配下を検出
- 4 ファイル（profile.json / equipment.json / pantry.json / meal_history.jsonl）の読み込み
- ディレクトリハンドルのセッション中保持
- 保存モード（自動 / 手動）を設定で切替できる仕組み
- ファイル書き込みユーティリティ（JSON / JSONL 両対応）
- 読み込みエラー・スキーマ不整合時のハンドリング（最低限の通知）

### Phase 0 が Phase 1 のために打った布石

| 布石 | Phase 1 への効果 |
|---|---|
| `providers/` ディレクトリを先取りで作成 | Phase 2 で LLM プロバイダー抽象化層を実装するとき、ディレクトリ追加の判断が不要になる |
| `DOM.Iterable` を `lib` に追加済み | Phase 1 で `for await...of` による `FileSystemDirectoryHandle` の反復処理を使っても型エラーが発生しない |
| `strict: true` を有効化済み | Phase 1 で書かれるファイルI/Oコードが最初から厳密な型チェックを受ける。外部データの型安全な取り扱いを強制できる |
| `noUnusedLocals: true` / `noUnusedParameters: true` が有効 | インポートしただけで使っていない変数・引数を早期に検出できる |
| `src/App.tsx` は意図的に未クリーンアップ | Phase 0 の受け入れテスト（`npm run dev` で初期画面確認）のために残している。Phase 1 着手時にアプリ固有の実装へ差し替える |

### Phase 1 着手前に確認すべき申し送り

1. **`src/App.tsx` / `src/App.css` / `index.css` のクリーンアップ**: coding-agent の完了報告に記載されている通り、Vite テンプレートの初期ファイルをアプリ固有の実装に差し替える必要がある。Phase 1 の指示書にこのクリーンアップを含めること。

2. **`tsconfig.app.json` の `erasableSyntaxOnly: true`**: Vite 8 テンプレートが追加した設定（TypeScript 5.5+ の機能、`const enum` 等を型消去可能な構文のみに制限する）。Phase 1 以降で `const enum` を使うと型エラーになる可能性があるため、認識しておく必要がある。

3. **型チェック単体コマンドの不在**: `package.json` に `tsc` スクリプト単体がないため `npm run tsc` は動作しない。型チェックのみを素早く実行したい場合は `"typecheck": "tsc -b --noEmit"` の追加を検討する（code-review-agent の S-2 指摘）。

4. **`src/assets/react.svg`**: Vite テンプレートが生成したサンプルアセット。Phase 1 のクリーンアップ時に削除を検討。

## 付録: 主要設定値の一覧

### `.prettierrc`

| 設定 | 値 | 意味 |
|---|---|---|
| `semi` | `true` | 文末にセミコロンを付ける |
| `singleQuote` | `true` | 文字列は単引用符 |
| `tabWidth` | `2` | インデント幅 2 スペース |
| `trailingComma` | `"es5"` | ES5 で有効な箇所（配列・オブジェクト末尾）にトレイリングカンマ |
| `printWidth` | `100` | 1行の最大文字数 100（80より広め、TypeScriptの型定義を読みやすくする） |
| `endOfLine` | `"lf"` | 改行コードを LF に統一（Windows 環境だが Git の CRLF 変換と競合しないよう明示） |

### `tsconfig.app.json` の主要フラグ

| フラグ | 値 | 意図 |
|---|---|---|
| `strict` | `true` | 厳密な型チェックを最大化（null チェック・暗黙的 any の禁止など） |
| `noUnusedLocals` | `true` | 未使用のローカル変数をエラーとして扱う |
| `noUnusedParameters` | `true` | 未使用の関数引数をエラーとして扱う |
| `noFallthroughCasesInSwitch` | `true` | switch 文のフォールスルーを禁止 |
| `lib` | `["ES2023", "DOM", "DOM.Iterable"]` | File System Access API の非同期イテレーター型を含む標準ライブラリセット |
| `erasableSyntaxOnly` | `true` | Vite 8 テンプレートが追加。型消去可能な構文のみ許可 |
