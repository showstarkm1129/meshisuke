## 1. 総評

Phase 1 は「バックエンドなし・ファイルシステムはユーザー選択フォルダのみ・外部通信なし」という設計方針を堅実に実装している。Critical 指摘はゼロ。High 指摘は 1 件（`console.error` / `console.warn` による潜在的な PII ログ出力）で、これは現時点でリスクが低いが、Phase 2 で LLM 通信が加わると意図しない PII 漏洩の起点になりうるため、Phase 2 着手前の修正を強く推奨する。Medium 指摘は 2 件、Low 指摘は 2 件。「食生活データが第三者サーバーに送信されない設計」というポリシーへの違反は現在の実装には存在しない。

Phase 1 を**完了**とみなすために Critical / High 相当の対処が必要か否か: **High 1 件について Phase 2 着手前に修正することを条件として、Phase 1 は通過可能とする。**

## 2. 指摘事項

---

### [High] H-1: `console.error` / `console.warn` による PII データのブラウザコンソール出力リスク

- **ファイル**: `app/src/lib/fileio.ts` 32行目、66行目、60行目
- **問題**:

```typescript
// 32行目
console.error(`[fileio] readJsonFile failed: ${fileHandle.name}`, err);

// 66行目
console.error(`[fileio] readJsonlFile failed: ${fileHandle.name}`, err);

// 60行目
console.warn(`[fileio] readJsonlFile: skipped malformed line ${i + 1} in ${fileHandle.name}`);
```

`readJsonFile` は `profile.json`（嗜好・健康情報・アレルギー・栄養目標）と `pantry.json`（食材在庫）を読み込む関数として呼び出される。`fileHandle.name` はファイル名のみであり PII そのものではないが、第2引数として渡される `err` オブジェクトによっては、ブラウザエラーメッセージにファイルパスや内部状態が含まれる場合がある。

より直接的なリスクは、将来 Phase 2 / 3 で LLM レスポンスを JSON パースする処理がこれらの関数を再利用した際に、**LLM が返した PII 含みの JSON 文字列がパース失敗時に `console.error` の第2引数 (`err`) に含まれる可能性がある**点である。`JSON.parse` の失敗時、V8 エンジンのエラーメッセージは入力文字列の一部を含むことがある（例: `SyntaxError: Unexpected token 'p', "{'name':..." is not valid JSON`）。

- **攻撃シナリオ**: ブラウザの開発者ツールへのアクセス権を持つ悪意ある拡張機能、または Chrome DevTools Protocol を悪用するツールが、コンソール出力から PII を取得する。Phase 2 以降でも同じログパターンを使い続けた場合、アレルギー情報・食事行動履歴・栄養情報がコンソールに流出するリスクがある。
- **影響範囲**: `readJsonFile`（profile / equipment / pantry の読み込み）、`readJsonlFile`（meal_history の読み込み）
- **推奨対応**: `console.error` の第2引数から `err` オブジェクトを除去し、ファイル名のみをログする。エラーの詳細は上位の呼び出し元（`useDataLoader`）でハンドルする設計に変更する。

```typescript
// 修正例
console.error(`[fileio] readJsonFile failed: ${fileHandle.name}`);
// err を throw して呼び出し元で処理させるか、または err.name のみを記録する
```

Phase 2 以降で LLM レスポンスの JSON パースを行う新しい関数を作成する際は、同様のパターンを避けること。

### [Medium] M-1: `useFolderPicker.ts` — エラーメッセージに `String(err)` を直接含める

- **ファイル**: `app/src/hooks/useFolderPicker.ts` 54行目
- **問題**:

```typescript
dispatch({
  type: 'ADD_ERROR',
  payload: `フォルダの読み込み中にエラーが発生しました: ${String(err)}`,
});
```

`String(err)` により、ブラウザが生成したエラーオブジェクトの文字列表現が直接 UI（ErrorBanner）に表示される。`DOMException` や `SecurityError` の `message` プロパティは、対象のファイルシステムパスや内部的な権限情報を含む場合がある（例: `"Failed to execute 'getDirectoryHandle' on 'FileSystemDirectoryHandle': The path 'C:\sensitive\path' is not a valid path."`）。

- **攻撃シナリオ**: 悪意を持った人物がユーザーのブラウザ画面を覗き見または操作した際に、ファイルシステムパスや OS の内部情報を取得できる可能性がある。特に Windows のフルパスが表示される場合、ホームディレクトリ名（ユーザー名）が露出する。
- **影響範囲**: フォルダ選択エラー時の UI 表示
- **推奨対応**: エラーオブジェクトを `String(err)` でそのまま UI に出さず、`err` が `DOMException` の場合は `err.name` のみを使い、その他は汎用メッセージを表示する。

```typescript
} catch (err) {
  if (err instanceof DOMException && err.name === 'AbortError') {
    return;
  }
  const detail = err instanceof DOMException ? err.name : '不明なエラー';
  dispatch({
    type: 'ADD_ERROR',
    payload: `フォルダの読み込み中にエラーが発生しました (${detail})。`,
  });
}
```

同様のパターンが `useFileSaver.ts` にも存在する（後述 M-2 参照）。

### [Medium] M-2: `useFileSaver.ts` — `String(err)` を UI 表示メッセージに含める（同パターン）

- **ファイル**: `app/src/hooks/useFileSaver.ts` 34行目、58行目、84行目、109行目、136行目、144行目、152行目
- **問題**: M-1 と同一パターン。各 `catch (err)` ブロックで `${String(err)}` を `ADD_ERROR` の payload に含めており、`ErrorBanner` 経由でそのまま UI に表示される。

```typescript
// 例: 34行目
payload: `profile.json の保存に失敗しました: ${String(err)}`,
```

保存失敗時のエラーは `FileSystemWritableFileStream` 由来の DOMException が多く、対象ファイルの OS レベルパスが含まれる可能性がある。

- **推奨対応**: M-1 と同様に、`err.name` のみを使う汎用メッセージに置き換える。または共通のエラーフォーマット関数（例: `formatUserError(err: unknown): string`）を作成して再利用する。

```typescript
function formatUserError(context: string, err: unknown): string {
  const detail = err instanceof DOMException ? err.name : (err instanceof Error ? err.name : '不明なエラー');
  return `${context} (${detail})`;
}
```

### [Low] L-1: `showDirectoryPicker` に `mode: 'readwrite'` を要求しているが `read` で足りる読み込み処理がある

- **ファイル**: `app/src/hooks/useFolderPicker.ts` 21行目
- **問題**:

```typescript
const rootHandle = await window.showDirectoryPicker({ mode: 'readwrite' });
```

ユーザーが最初にフォルダを選択する際に `readwrite` 権限を要求している。この権限要求は適切ではあるが、権限最小化の観点から確認が必要である。

現状、`mode: 'readwrite'` は書き込み操作（`useFileSaver`）を行うために必要であり、過剰な権限要求ではない。ただし、**保存モードが `manual` に設定されており実際には書き込みを行わないセッションでも `readwrite` を要求する**点は、「必要最小限の権限を要求する」原則からはずれている。

- **攻撃シナリオ**: 悪意ある拡張機能や XSS 脆弱性が将来混入した場合に、`readwrite` 権限を悪用してユーザー選択フォルダ配下の任意ファイルを書き換えられるリスクがある（現時点では XSS は存在しない）。
- **影響範囲**: ブラウザの権限ダイアログでユーザーに表示される権限レベル
- **推奨対応**: Phase 1 スコープでは許容範囲。Phase 2 以降で以下を検討: 初回は `mode: 'read'` で選択させ、書き込み操作が発生するタイミングで権限昇格を要求する（ただし実装コストが高く、UX も複雑になるため MVP では現状維持が妥当）。

### [Low] L-2: `localStorage` にアプリ設定以外のデータが将来書き込まれるリスクへの予防的注意

- **ファイル**: `app/src/providers/AppStateContext.tsx` 49行目
- **問題**:

```typescript
case 'SET_SAVE_MODE': {
  localStorage.setItem('meshisuke_save_mode', action.payload);
  return { ...state, saveMode: action.payload };
}
```

現時点では `localStorage` に書き込まれるのは `meshisuke_save_mode`（`'auto'` または `'manual'`）のみであり、PII は含まれていない。これは正しい設計である。

**ただし**、`AppState` には `profile`（嗜好・健康情報）・`pantry`（在庫）・`mealHistory`（食事履歴）が含まれており、将来 Reducer に新しい Action が追加される際に、誤って PII を `localStorage.setItem` に渡すコードが混入するリスクがある。現在の実装でも、`'SET_SAVE_MODE'` ケース内の `localStorage.setItem` は `action.payload` が検証済みの `SaveMode` 型に限定されているため安全である（W-2 の `parseSaveMode` 修正後）。

- **リスク**: Low（現時点では問題なし。将来の拡張時の注意事項）
- **推奨対応**: `localStorage` へのアクセスを `AppStateContext` の Reducer 内に閉じ込めている設計は正しい。Phase 2 以降で新しい永続化ニーズが出た場合に、PII を localStorage に書き込まないルールをチームで明示化すること（CLAUDE.md またはコメントへの記載を推奨）。

## 4. Phase 2 着手前に必ず再監査が必要な観点

Phase 2（LLM プロバイダー抽象化）では以下の新リスクが発生するため、Phase 2 実装完了時に Security-Check-agent による再監査を行うこと。

### 4-A: API キー管理（Critical 級リスクの可能性）

- BYO Key（ユーザーが自分の API キーを入力する）方式を採用予定。API キーをメモリ内のどこに保持するかが最重要チェック項目。
- **禁止事項**: `localStorage` / `sessionStorage` への API キー保存（XSS により盗取可能）、`console.log` / `console.error` への API キー出力
- **推奨**: React State（インメモリ）に保持し、セッションをまたいで永続化しない。またはブラウザの `Window.crypto.subtle` を使った保護を検討。
- Phase 2 で API キー入力 UI・保存ロジック・LLM 呼び出しロジックが追加された時点でレビュー必須。

### 4-B: LLM レスポンスに含まれる PII のログ出力

- Phase 1 で指摘した `console.error(err)` パターン（H-1）が修正されていない場合、LLM レスポンスの JSON パースエラー時に応答全文がコンソールに流出する可能性がある。H-1 の修正を Phase 2 着手前に完了させること。

### 4-C: LLM へのリクエストボディに含まれる PII

- `profile.json`（アレルギー・嗜好・健康目標）、`meal_history.jsonl`（食事行動履歴）を LLM プロンプトに含めて送信する設計になる予定。これは README のポリシー（「食生活データが第三者サーバーに送信されない設計」）と**矛盾するように見える**が、BYO Key 方式では「ユーザー自身の API エンドポイントに送る」という理解で設計されているものと推察される。この点をユーザー向けのプライバシー説明（UI またはドキュメント）で明確化しておくこと。

### 4-D: CORS・CSP 設定

- Phase 2 でブラウザから LLM API（api.anthropic.com / api.openai.com 等）への直接 fetch が発生する。Vite の本番ビルド時に Content Security Policy ヘッダーまたは `<meta>` タグの設定を忘れないこと。特に `connect-src` に許可ドメインを限定することで、XSS 経由の外部通信先を絞ることができる。

### 4-E: エラーメッセージからの API キー / エンドポイント情報漏洩

- LLM API の 401 / 429 / 5xx エラー時に、レスポンスボディをそのまま `ErrorBanner` に表示しないこと。API プロバイダーによってはレスポンスに API キーの一部が含まれる場合がある。

## 5. 良好な点

### 5-1: File System Access API の権限スコープ制御

`getFileHandle` / `getDirectoryHandle` が常にユーザーが選択した `rootHandle` の子孫に限定されている。ファイル名は `REQUIRED_FILES` 定数（`'profile.json'`, `'equipment.json'`, `'pantry.json'`, `'meal_history.jsonl'`）または `'data'`（ディレクトリ名）のハードコード値のみが使用されており、ユーザー入力がファイル名・パスに動的に使われるコードパスは存在しない。これによりディレクトリトラバーサル相当のリスクは排除されている。

### 5-2: `parseSaveMode` による localStorage 値の検証（W-2 修正対応済み）

`AppStateContext.tsx` の `parseSaveMode` 関数は、`localStorage` から取得した値が `'auto'` / `'manual'` 以外の場合に `'auto'` へフォールバックする。型キャストを排除した堅牢な実装であり、localStorage 汚染攻撃に対して適切に対処している。

### 5-3: `writeJsonFile` / `appendJsonlRecord` の `try/catch/abort` パターン

ファイル書き込み中にエラーが発生した場合に `writable.abort()` を呼び出し、ファイルの中途半端な書き込みを防ぐ設計が正しく実装されている。ユーザーの PII データが破損した状態で保存されるリスクを軽減している。

### 5-4: `AbortError` のキャンセル処理

`useFolderPicker.ts` において、ユーザーがダイアログをキャンセルした場合（`AbortError`）を正しくハンドルしてエラーメッセージを表示しない実装になっている。誤ったエラー情報でユーザーを混乱させない適切な実装。

### 5-5: localStorage への PII 非書き込み

現状 `localStorage` に書き込まれているのは `meshisuke_save_mode`（`'auto'` または `'manual'`）のみであり、profile / pantry / mealHistory といった PII は localStorage に書き込まれていない。「食生活データが第三者サーバーに送信されない設計」ポリシーと整合している。

### 5-6: ErrorBanner の XSS 安全性

`ErrorBanner.tsx` は `dangerouslySetInnerHTML` を使用しておらず、エラーメッセージ文字列は React の `{msg}` テキストノードとして描画されるため、HTML インジェクションは発生しない。エラーメッセージに悪意のある文字列が含まれても DOM を汚染できない。

### 5-7: 外部依存パッケージの追加なし

`package.json` に Phase 0 からの追加 npm パッケージは存在しない（`dependencies` は `react` / `react-dom` のみ）。サードパーティライブラリへの PII 流入リスクがゼロに保たれている。

### 5-8: バリデーション前の `SET_DIR_HANDLE` dispatch 削除（W-1 修正対応済み）

`useFolderPicker.ts` の 22行目にあった、バリデーション前の `SET_DIR_HANDLE` dispatch が削除されており、バリデーション済みのハンドルのみが State に入る設計に整合している。バリデーション未完了のタイミングでデータ読み込みが走るリスクが排除されている。

## 6. 総括コメント

Phase 1 の実装は、ローカルファイル I/O 専用フェーズとして適切なセキュリティ設計を持っている。Critical 指摘はゼロ。最も注目すべき指摘は H-1 の `console.error(err)` パターンで、これは現時点では低リスクだが Phase 2 以降でリスクが拡大する構造的問題であるため早期修正を推奨する。

PII の扱いとして特に重要な点: profile.json に含まれるアレルギー情報・食事制限・栄養目標、および meal_history.jsonl に含まれる日々の食事行動履歴はセンシティブな個人情報であり、これらが意図しない経路（console / localStorage / UI エラーメッセージ）に露出しないよう、Phase 2 以降も継続的な注意が必要である。

README の「食生活データが第三者サーバーに送信されない設計」というポリシーは現在の実装では遵守されている。ただし Phase 2 で LLM API への送信が加わった時点でこのポリシーは「第三者ではなくユーザー自身の API キーが向かうエンドポイント」という文脈の明確化が必要になる。ユーザーへの適切な説明設計を Phase 2 で検討すること。
